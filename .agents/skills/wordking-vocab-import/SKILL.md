# 單字王｜手寫單字匯入與 90% 校對

這是「單字王」專案專用、可重複執行的手寫照片轉結構化公用單字流程。請用繁體中文和使用者溝通。若本次只要求「整理」或「核對」，只交付清單與疑問；若明確要求「推回去／更新網站／匯入網站」，完成下述閘門後才提交 GitHub。

**目標專案：** `stu310101-arch/wordking`（main 分支）；網站 `https://stu310101-arch.github.io/wordking/`。先讀 [references/schema-and-checks.md](references/schema-and-checks.md)；需要判斷前次已確認的爭議字時再讀 [references/confirmed-terms.md](references/confirmed-terms.md)。以最新專案實際檔案為準，不把參考檔當作不會變的快照。

## 強制規則（不可略過）

1. **90% 才錄入。** 對每筆英文拼字、每個中文解釋、每一個詞性標記分別評估辨識把握。任何一項低於 **90%**，不要把推測文字寫進單字資料。將「原照片位置、看得出的字、目前候選解讀、缺乏把握的原因」列給使用者確認；使用者回覆前保留待確認狀態。也不要用字典常見意思、語境或既有網頁內容代替照片原文。
2. **無聲修改禁止。** 如果筆記的詞性與標準字典不一致、已存在的網站解釋不同、筆記出現可能的筆誤，列為「與原稿或既有資料有差異」，先問使用者；不能自作主張改詞性、補寫意思、刪除或替換使用者的內容。已確認過的個案參閱 confirmed-terms。
3. **先完整校對再發布。** 按照片每一欄由上到下列出所有英文，數量與範圍要確認；逐筆檢查中文／詞性／標點；所有未達 90% 的疑問集中列出。未回答的詞條不得提交；如整回需完整匯入，先停在待確認狀態，清楚告知缺哪些。
4. **不能破壞既有個人資料或歷史身分。** 既有英文沿用其 opaque word ID、先前課程、意思及 `isWrong`；同詞性只補充經確認且不重複的解釋。新英文字才配發新的 `w_######`，以 Git 配發歷史和目前最大號核對，不以固定數字起算，也不能回收曾用 ID。不要修改 `migration/` 凍結檔或 Firestore 個人資料。
5. **名字精準。** 課程 ID 與顯示名稱都以使用者指定字串為準，尤其 `L5` 和 `Lv5` 不可擅自互換；不因顯示名稱相同而合併課程 identity。
6. **別假裝測試或推送成功。** 能執行的驗證必須實際執行；若只能靜態驗證，明講限制。推送後重新讀取 GitHub main 分支並回報 commit、更新單字／沿用單字數與尚未確認的項目。

## 標準工作流程

### A. 辨識原稿並製作稽核清單

- 先取得使用者提供的原始圖片／檔案，必要時旋正、放大、分欄裁切。不要因單字順序看似合理就忽略欄位，按「左欄由上而下，右欄由上而下」讀取。
- 對每筆建立內部校對紀錄：`lessonId, english, partOfSpeech, definitions[], sourcePage/column/row, confidence, notes`；confidence 是辨識自信，**不能**把字典正確度當作看清字跡的自信。
- 保留每個詞性所屬的解釋，例如「同字有名詞／動詞」要分組；`n.`→`noun`、`v.`→`verb`、`a./adj.`→`adjective`、`adv.`→`adverb`。無法看清是否標註詞性時詢問，勿猜。
- 建立「待確認」列表；單一字含一個未確定義項時也要標示。問法直接，例如：「L5U11 `graphic` 第三個意思，我看不清，請確認是什麼？」不提供暗示性的假定答案作定論。
- 避免錯誤串欄、少字、重複或混合兩張圖。逐課清點原稿英文數量，不用之前的 40／42 當未來照片的固定數量。

### B. 先比對現有 GitHub 公用資料

- 從 GitHub 讀取當前 `data/words.json`、`assets/word-data.js`、`tests/word-data.test.cjs` 和架構說明。優先使用已連線的 GitHub 工具或具權限的本機工作樹，**不得依賴過期的對話版本**。
- 以 `english.trim().toLowerCase()` 對照現有字。每個英文只保留一個實體；舊字保留原 `id`、其他 `lessonIds`、`isWrong`；按詞性合併新中文，不生成一筆同英文的重複實體。
- 不要合併字形不同的單字；也不要把語意相近的詞當同一筆。
- 舊值與照片衝突：保留舊值，單獨報告差異，取得明確修正授權才替換。接近重複的標點／同義詞可以提出建議，但不私自刪改歷史定義。
- 匯入前確認「新建／沿用／未解」數量，避免不同來源計數不一致。

### C. 轉成網站標準陣列

- 使用 schema v6：`[{id, english, meanings:[{partOfSpeech,definitions:[]}], lessonIds:[], isWrong}]`。
- `partOfSpeech` 必須是網站支援的完整 enum；同詞性只出現一組；`definitions` 是繁體中文字符串陣列，不混入 `(n.)`、`(v.)`。
- `meanings` 的組別順序使用 `assets/word-data.js` 所定 enum 順序；維持清晰的資料結構和 JSON 縮排風格。
- 在 `assets/word-data.js` 的 `PUBLIC_LESSONS` 註冊新課程；修改相關匯入測試的完整英文集合、沿用身分、課程歸屬與最新字庫總數／membership 總數，確保歷史測試也納入新課程且不誤判失敗。
- 僅在必要時更新 `DATA-ARCHITECTURE.md` 的統計與匯入紀錄。**不重建、刪除或改寫** `migration/`。

### D. 檢查與發布

1. 稽核 `words.json`：JSON 合法；英文大小寫不敏感的唯一性；ID 唯一；每詞性唯一；definition 不空白、不在中文字內留 POS 縮寫；既有 identity、lesson membership 和私人資料未被破壞。
2. 有本機執行環境時，在 repo `config/` 下跑 `npm run validate:data` 與 `npm test`（詳見 schema-and-checks）；測試錯誤先修復，不可把舊硬編碼的預期數字當永恆事實。
3. 推送前重新確認分支 HEAD；優先用單一 atomic commit 寫入，更新 main 時使用預期 HEAD／非 force 更新，遇到衝突重新抓取並套用，不能覆蓋別人的 commit。
4. 推送後重新讀取資料和分支 SHA，確認課程數量、字串、意思與 commit 均確實到位；網站發布可能另需時間或部署，不把 commit 成功等同於前端已上線。
5. 回覆：兩回名稱、各課單字數、新字／沿用數、是否已推送、驗證結果、commit 連結，並逐項列出未解／使用者待確認部分。沒有執行的測試不得報成通過。

## 特別避免之前發生的錯誤

- `graphic` 手寫的是「寫實的、電繪的」，**不是血腥的**。這是已確認錯誤，見 references。
- `extension` 為名詞「延期、延長、擴大」；`fraud` 原稿本來就是名詞；`glisten` 只有動詞。不要把前一次模型的錯誤判讀再當成需使用者修正的「原始筆記」。
- 低於 90% 的手寫中文必須問，不要自己猜、先推再問。
